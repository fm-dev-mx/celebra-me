## Purpose and boundaries

Guest engagement analytics answers, for the event host, "who opened the invitation, how many times,
how far they read, and whether they responded", and, for Celebra-me, "which invitations and designs
engage guests best".

- **First-party and guest-scoped.** Events are stored only in Celebra-me's database, keyed to a
  guest invitation while the retention window lasts.
- **Isolated from commercial attribution.** Guest engagement never feeds `tracking_events`,
  `visitor_sessions`, GA4, Meta, or Vercel Analytics, and never joins them. Personalized and real
  invitation routes stay excluded from commercial tracking
  ([`../tracking/commercial-attribution.md`](../tracking/commercial-attribution.md)).
- **Data minimization.** No IP address, raw user agent, or free text is stored. Device information
  is reduced to a coarse class.
- **Fail-open for guests.** Tracking failures never affect page rendering or RSVP submission.

## Event taxonomy (schema version 1)

The taxonomy is closed. Unknown event names or properties are rejected at the API edge and by
database check constraints.

### Envelope

| Field             | Type        | Notes                                                                                |
| ----------------- | ----------- | ------------------------------------------------------------------------------------ |
| `client_event_id` | uuid        | Idempotency key; generated by the client, or deterministically by the server         |
| `schema_version`  | smallint    | `1`                                                                                  |
| `event_name`      | enum        | See below                                                                            |
| `occurred_at`     | timestamptz | Client time, clamped to `[received_at - 24h, received_at + 5m]`                      |
| `received_at`     | timestamptz | Server time                                                                          |
| `page_view_id`    | uuid / null | Random per page load; correlates events of one load; null for server-only events     |
| `traffic_class`   | enum        | See [Traffic classification](#traffic-classification)                                |
| `device_class`    | enum        | `mobile`, `tablet`, `desktop`, `unknown`; derived server-side, user agent not stored |
| `properties`      | jsonb       | Per-event schema below; no other keys allowed                                        |

### Events

| Event                       | Emitted by                                      | Properties                                                    |
| --------------------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| `invitation_link_previewed` | Server, short-link crawler branch               | `crawler_family`: `whatsapp`, `facebook`, `telegram`, `other` |
| `invitation_opened`         | Client, once per page load after ≥ 1 s visible  | `entry`: `short_link`, `direct`; `is_reload`: boolean         |
| `invitation_progressed`     | Client, when a depth milestone is first crossed | `milestone`: 25, 50, 75, 100                                  |
| `rsvp_form_viewed`          | Client, RSVP section visible                    | —                                                             |
| `rsvp_form_started`         | Client, first interaction with the RSVP form    | —                                                             |
| `rsvp_submitted`            | Server, after a successful RSVP persistence     | `attendance_status`: `confirmed`, `declined`                  |

Depth is the share of rendered sections (`[data-section-id]`) seen at ≥ 20 % visibility.
`rsvp_submitted` is server truth; the client never emits it.

Reserved for a later schema version (names are stable, not implemented): `cta_clicked` with `cta` in
`map`, `calendar`, `gift_registry`, `whatsapp_host`, `music_play`, `gallery`.

## Traffic classification

Every stored event carries exactly one class. Only `guest` traffic counts in host metrics, guest
projections, and invitation snapshots. Other classes are stored for auditability and share the same
retention.

| Class            | Rule (first match wins)                                                      |
| ---------------- | ---------------------------------------------------------------------------- |
| `non_production` | Request served outside Vercel Production (`VERCEL_ENV !== 'production'`)     |
| `bot`            | User agent matches the crawler/bot list (link previews are always `bot`)     |
| `host`           | Valid session of the event owner, an active event member, or a `super_admin` |
| `test`           | Guest invitation flagged as a test guest (`is_test`)                         |
| `guest`          | Everything else                                                              |

Session lookup runs only when an auth cookie is present, so ordinary guests pay no extra latency.
In-app browsers (Instagram, Facebook, WhatsApp webviews) are humans, not crawlers.

## Metrics dictionary

All metrics use `traffic_class = 'guest'` unless stated. UI copy must map to one of these
definitions; it must not introduce new metrics.

### Per guest

| Metric              | Definition                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------ |
| Opens               | Distinct `page_view_id` with `invitation_opened`                                           |
| Visits              | Opens grouped into sessions separated by ≥ 30 minutes of inactivity (derived at read time) |
| First / last opened | Min / max `occurred_at` of `invitation_opened`                                             |
| Previewed           | At least one `invitation_link_previewed` (any class)                                       |
| Max depth           | Max `milestone` of `invitation_progressed`                                                 |

Hosts see opens, first/last opened dates, max depth, and previewed yes/no per guest. Device class
and detailed timestamps are not shown per guest.

### Per event (host dashboard)

| Metric                | Definition                                                                |
| --------------------- | ------------------------------------------------------------------------- |
| Funnel                | Guest counts for shared → opened → form viewed → form started → responded |
| Opened, not responded | Opened guests with `attendance_status = 'pending'`                        |
| Time to open          | Median of `first_opened_at - first_shared_at`                             |

The funnel is monotonic: each step counts only guests counted in every previous step. "Previewed" is
shown beside the funnel, not as a required step.

Engagement metrics start at the activation date and are labeled "desde {fecha}". Historic
`guest_invitation_audit` `viewed` rows are not backfilled: before activation, one page load wrote
several rows, so they do not represent opens.

### Per invitation (permanent snapshots)

| Metric          | Definition                                                                   |
| --------------- | ---------------------------------------------------------------------------- |
| Open rate       | Opened guests / shared guests                                                |
| Completion rate | Guests with max depth 100 / opened guests                                    |
| RSVP conversion | Guests with a submitted RSVP / opened guests                                 |
| Reopen ratio    | Opens / opened guests (ambiguous: interest or confusion; never ranked alone) |
| Time to respond | Median of `responded_at - first_opened_at`                                   |
| Mobile share    | Opens with `device_class = 'mobile'` / opens                                 |

Rates are null when the denominator is zero.

### Comparison rules

Comparisons across invitations or designs must:

- compare only within the same event type;
- require at least 20 shared guests per invitation, and at least 5 invitations per design group;
- rank on rates, never on raw totals, which scale with guest count;
- show host-behavior covariates (share lead time, reminder coverage) next to every comparison;
- be treated as hypotheses, not verdicts.

## Storage tiers and retention

| Tier              | Content                                                      | Retention                                                                                      |
| ----------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Raw events        | Per-guest event log (`guest_engagement_events`)              | Linked to the guest until `events.event_date + 180 days`, then anonymized and kept permanently |
| Guest projections | Per-guest counters and dates on `guest_invitations`          | Until the guest is deleted                                                                     |
| Snapshots         | Per-invitation aggregates + design attributes, no guest data | Permanent                                                                                      |

- **Anonymization** clears `guest_invitation_id` and sets `anonymized_at`. Anonymous events keep
  only the event reference, event name, timestamps, the random `page_view_id`, device class, traffic
  class, and properties. They are internal-only and never shown to hosts.
- **Missing event date:** retention falls back to the newest `occurred_at` of the invitation's
  events + 180 days.
- **Ordering guarantee:** an invitation's events are anonymized only after its snapshot is newer
  than its newest raw event.
- **Deletion requests:** hard-deleting a guest cascades its non-anonymized events.

### Event date

`events.event_date` (date, event-local) follows `resolveInvitationSchedule`
(`src/lib/intake/invitation-validity.ts`) and is written on publish:

1. `eventTiming.localDateTime` (date part);
2. `eventTiming.startsAtUtc` converted to `eventTiming.timeZone` (default `America/Chihuahua`);
3. legacy `hero.date` (date part; floating local date even when suffixed with `Z`).

Demos have no event date.

### Snapshot design attributes

Snapshots capture the published content's design at compute time, with a `design_schema_version`:

| Attribute        | Source (published content)                                                    |
| ---------------- | ----------------------------------------------------------------------------- |
| Theme preset     | `theme.preset`, `theme.fontFamily`                                            |
| Template         | `templateId`, `visualProfileId` (optional)                                    |
| Sections         | Ordered `sectionOrder` keys that render (key listed and section data present) |
| Section variants | `variant` of each rendered section, plus `rsvp.personalizedAccess.variant`    |
| Music            | Present when `music.url` is playable; `music.autoPlay`                        |
| RSVP mode        | `rsvp.accessMode`, `rsvp.confirmationMode`                                    |

Snapshots never contain guest identifiers, names, phone numbers, or free text.

## Privacy notice requirements

The privacy policy (`src/pages/privacidad.astro`) must state, in Spanish ("usted"):

- that guest invitation opens, reading depth, and device class are recorded;
- that per-guest data is shown only to the event host and is not shared with third parties;
- the retention: identifiable for 180 days after the event, then anonymized;
- that anonymous aggregated statistics are kept to improve the service.
