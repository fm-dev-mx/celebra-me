> **Status: live in Production since 2026-10-12 (v0.20.0-beta.1).** Ledger and projections:
> `supabase/migrations/20261010120000_guest_engagement_events.sql`; snapshots and anonymization:
> `20261010130000_invitation_engagement_snapshots.sql`; ingestion:
> `/api/invitacion/:inviteId/events` (`src/lib/rsvp/engagement/`); browser:
> `src/lib/invitation/invitation-analytics.ts`; maintenance: `GET /api/cron/engagement-maintenance`.
> The legacy `/view` route is gone and `track_guest_invitation_view_public` is dropped by the
> contract migration `20261013110000`.

## Purpose and boundaries

Guest engagement analytics answers, for the event host, "who opened the invitation, how many times,
how far they read, and whether they responded", and, for Celebra-me, "which invitations and designs
engage guests best".

- **First-party and guest-scoped.** Events are stored only in Celebra-me's database, keyed to a
  guest invitation while the retention window lasts.
- **Isolated from commercial attribution.** Guest engagement never feeds `tracking_events`,
  `visitor_sessions`, GA4, Meta, or Vercel Analytics, and never joins them. Personalized and real
  invitation routes stay excluded from commercial tracking
  ([`../tracking/commercial-attribution.md`](../tracking/commercial-attribution.md)).
- **Data minimization.** No IP address, raw user agent, or free text is stored. Device information
  is reduced to a coarse class.
- **Fail-open for guests.** Tracking failures never affect page rendering or RSVP submission.

## Event taxonomy (schema version 1)

The taxonomy is closed. Unknown event names or properties are rejected at the API edge and by
database check constraints.

### Envelope

| Field             | Type        | Notes                                                                                |
| ----------------- | ----------- | ------------------------------------------------------------------------------------ |
| `client_event_id` | uuid        | Idempotency key; generated by the client, or deterministically by the server         |
| `schema_version`  | smallint    | `1`                                                                                  |
| `event_name`      | enum        | See below                                                                            |
| `occurred_at`     | timestamptz | Client time, clamped to `[received_at - 24h, received_at + 5m]`                      |
| `received_at`     | timestamptz | Server time                                                                          |
| `page_view_id`    | uuid / null | Random per page load; correlates events of one load; null for server-only events     |
| `traffic_class`   | enum        | See [Traffic classification](#traffic-classification)                                |
| `device_class`    | enum        | `mobile`, `tablet`, `desktop`, `unknown`; derived server-side, user agent not stored |
| `properties`      | jsonb       | Per-event schema below; no other keys allowed                                        |

### Events

| Event                       | Emitted by                                      | Properties                                                    |
| --------------------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| `invitation_link_previewed` | Server, short-link crawler branch               | `crawler_family`: `whatsapp`, `facebook`, `telegram`, `other` |
| `invitation_opened`         | Client, once per page load after ≥ 1 s visible  | `entry`: `short_link`, `direct`; `is_reload`: boolean         |
| `invitation_progressed`     | Client, when a depth milestone is first crossed | `milestone`: 25, 50, 75, 100                                  |
| `rsvp_form_viewed`          | Client, RSVP section visible                    | —                                                             |
| `rsvp_form_started`         | Client, first interaction with the RSVP form    | —                                                             |
| `rsvp_submitted`            | Server, after a successful RSVP persistence     | `attendance_status`: `confirmed`, `declined`                  |

Depth is the share of rendered sections (`[data-section-id]`) seen at ≥ 20 % visibility.
`rsvp_submitted` is server truth; the client never emits it.

Reserved for a later schema version (names are stable, not implemented): `cta_clicked` with `cta` in
`map`, `calendar`, `gift_registry`, `whatsapp_host`, `music_play`, `gallery`.

## Traffic classification

Every stored event carries exactly one class. Only `guest` traffic counts in host metrics, guest
projections, and invitation snapshots. Other classes are stored for auditability and share the same
retention.

| Class            | Rule (first match wins)                                                      |
| ---------------- | ---------------------------------------------------------------------------- |
| `non_production` | Request served outside Vercel Production (`VERCEL_ENV !== 'production'`)     |
| `bot`            | User agent matches the crawler/bot list (link previews are always `bot`)     |
| `host`           | Valid session of the event owner, an active event member, or a `super_admin` |
| `test`           | Guest invitation flagged as a test guest (`is_test`)                         |
| `guest`          | Everything else                                                              |

Session lookup runs only when an auth cookie is present, so ordinary guests pay no extra latency.
In-app browsers (Instagram, Facebook, WhatsApp webviews) are humans, not crawlers.

## Metrics dictionary

All metrics use `traffic_class = 'guest'` unless stated. UI copy must map to one of these
definitions; it must not introduce new metrics.

### Per guest

| Metric              | Definition                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------ |
| Opens               | Distinct `page_view_id` with `invitation_opened`                                           |
| Visits              | Opens grouped into sessions separated by ≥ 30 minutes of inactivity (derived at read time) |
| First / last opened | Min / max `occurred_at` of `invitation_opened`                                             |
| Previewed           | At least one `invitation_link_previewed` (any class)                                       |
| Max depth           | Max `milestone` of `invitation_progressed`                                                 |

Hosts see opens, first/last opened dates, max depth, and previewed yes/no per guest. Device class
and detailed timestamps are not shown per guest.

### Per event (host dashboard)

| Metric                | Definition                                                                |
| --------------------- | ------------------------------------------------------------------------- |
| Funnel                | Guest counts for shared → opened → form viewed → form started → responded |
| Opened, not responded | Opened guests with `attendance_status = 'pending'`                        |
| Time to open          | Median of `first_opened_at - first_shared_at`                             |

The funnel is monotonic: each step counts only guests counted in every previous step. "Previewed" is
shown beside the funnel, not as a required step.

Engagement metrics start at the activation date and are labeled "desde {fecha}". Historic
`guest_invitation_audit` `viewed` rows are not backfilled: before activation, one page load wrote
several rows, so they do not represent opens.

### Per invitation (permanent snapshots)

| Metric          | Definition                                                                   |
| --------------- | ---------------------------------------------------------------------------- |
| Open rate       | Opened guests / shared guests                                                |
| Completion rate | Guests with max depth 100 / opened guests                                    |
| RSVP conversion | Guests with a submitted RSVP / opened guests                                 |
| Reopen ratio    | Opens / opened guests (ambiguous: interest or confusion; never ranked alone) |
| Time to respond | Median of `responded_at - first_opened_at`                                   |
| Mobile share    | Opens with `device_class = 'mobile'` / opens                                 |

Rates are null when the denominator is zero.

### Comparison rules

Comparisons across invitations or designs must:

- compare only within the same event type;
- require at least 20 shared guests per invitation, and at least 5 invitations per design group;
- rank on rates, never on raw totals, which scale with guest count;
- show host-behavior covariates (share lead time, reminder coverage) next to every comparison;
- be treated as hypotheses, not verdicts.

## Storage tiers and retention

| Tier              | Content                                                      | Retention                                                                                      |
| ----------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Raw events        | Per-guest event log (`guest_engagement_events`)              | Linked to the guest until `events.event_date + 180 days`, then anonymized and kept permanently |
| Guest projections | Per-guest counters and dates on `guest_invitations`          | Until the guest is deleted                                                                     |
| Snapshots         | Per-invitation aggregates + design attributes, no guest data | Permanent                                                                                      |

- **Anonymization** clears `guest_invitation_id` and sets `anonymized_at`. Anonymous events keep
  only the event reference, event name, timestamps, the random `page_view_id`, device class, traffic
  class, and properties. They are internal-only and never shown to hosts.
- **Missing event date:** retention falls back to the newest `occurred_at` of the invitation's
  events + 180 days.
- **Ordering guarantee:** an invitation's events are anonymized only after its snapshot is newer
  than its newest raw event.
- **Deletion requests:** hard-deleting a guest cascades its non-anonymized events.

### Event date

`events.event_date` (date, event-local) follows `resolveInvitationSchedule`
(`src/lib/intake/invitation-validity.ts`) and is written on publish:

1. `eventTiming.localDateTime` (date part);
2. `eventTiming.startsAtUtc` converted to `eventTiming.timeZone` (default `America/Chihuahua`);
3. legacy `hero.date` (date part; floating local date even when suffixed with `Z`).

Demos have no event date.

### Snapshot design attributes

Snapshots capture the published content's design at compute time, with a `design_schema_version`:

| Attribute        | Source (published content)                                                    |
| ---------------- | ----------------------------------------------------------------------------- |
| Theme preset     | `theme.preset`, `theme.fontFamily`                                            |
| Template         | `templateId`, `visualProfileId` (optional)                                    |
| Sections         | Ordered `sectionOrder` keys that render (key listed and section data present) |
| Section variants | `variant` of each rendered section, plus `rsvp.personalizedAccess.variant`    |
| Music            | Present when `music.url` is playable; `music.autoPlay`                        |
| RSVP mode        | `rsvp.accessMode`, `rsvp.confirmationMode`                                    |

Snapshots never contain guest identifiers, names, phone numbers, or free text.

### Ranking query v1 (phase 2, retired)

Retired by contract `20261014120000` once the v2 client was deployed; kept here as history.
`list_invitation_engagement_ranking(p_event_type text, p_group_key text default 'themePreset')`
(`20261013120000`, `security definer`, execute granted to `service_role` only) returned the rows the
administrator's ranking view compared. It applies the comparison rules in the database:

- same event type only; `metrics_version = 1` rows;
- one snapshot per event: `final` when it exists, else `rolling`; snapshots whose event was deleted
  (`event_id` null) are returned with `event_deleted = true` and no label;
- `sample_state` is `eligible` when `guests_shared >= 20`, otherwise `insufficient`;
- `group_value` is the design attribute selected by `p_group_key` (`themePreset`, `templateId`,
  `fontFamily`, `visualProfileId`, `personalizedAccessVariant`, `rsvpConfirmationMode`,
  `rsvpAccessMode`, `musicEnabled`; unknown keys raise `22023`), with `group_size` and
  `group_eligible` counted per value (`null` groups rows without design data).

Ranks and medians are computed by the application
(`src/lib/rsvp/engagement/engagement-ranking.service.ts`); a group is ranked only when
`group_eligible >= 5`, and insufficient rows are shown, never hidden. The routine never reads
`guest_engagement_events` or `guest_invitations`.

### Confidence levels (phase 2.1)

Engagement started on 2026-10-12, but older signals exist. The ranking keeps three levels apart and
labels every figure with its level; a figure never mixes levels.

| Level               | Source                                                                                     | Meaning           |
| ------------------- | ------------------------------------------------------------------------------------------ | ----------------- |
| Measured            | Ledger since 2026-10-12, guest traffic only                                                | Observed          |
| Inferred            | A guest who responded through the invitation opened it (`last_response_source <> 'admin'`) | Exact lower bound |
| Historical estimate | Legacy `viewed` audit rows before the ledger (2026-10-12 16:25 UTC), cleaned (below)       | Range, frozen     |

Definitions (computed live from guest projections; snapshots are unchanged):

- **Responded by guest**: `attendance_status <> 'pending'` and `last_response_source <> 'admin'`
  (host-entered responses never count as guest behavior).
- **Opened (inferred)**: opened (measured) or responded by guest.
- **Response rate**: responded by guest ÷ shared guests. Exact for every invitation, independent of
  open tracking, and the default ranking metric.
- **Conversion (upper bound)**: responded by guest ÷ opened (inferred). Opens inferred from
  responses make it tautologically high when few opens were measured, so it is shown as an upper
  bound («≤») and only narrowed into a range by the historical estimate. It is not measurable when
  `rsvp.confirmationMode = 'whatsapp'` (replies never reach the database) and partial for `both`;
  neither enters a conversion ranking.
- **Historical estimate**: see [Historical estimate](#historical-estimate-phase-21). It is shown in
  its own view, never ranked and never mixed with measured or inferred figures.

### Historical estimate (phase 2.1)

Migration `20261017120000` adds `invitation_engagement_historical_estimates` (one row per event and
`method_version`, aggregates only, RLS forced, `service_role` select) and two `service_role`
routines: `compute_engagement_historical_estimates(p_method_version)` computes every row of a
version once (re-running it is a no-op) and
`list_engagement_historical_estimates(p_event_type, p_method_version)` lists the rows of published
client invitations. The migration computes version 1 in its body. Method version 1 (validated on
2026-10-17 against the ledger):

- **Cutoff**: only `viewed` audit rows before 2026-10-12 16:25 UTC count; from then on the ledger
  also writes `viewed` audit rows, which are measured traffic.
- **Counted view**: at least 2 minutes after the guest's `first_shared_at`. Earlier rows are counted
  apart as before-share (host review, QA) or preview-window (chat link preview) views.
- **Viewed guest**: any counted view, not only the first one (first-view-only misses 13 % of real
  opens; any-view keeps 94 % precision and 99 % recall).
- **Opens range**: guests who responded by guest before the cutoff (lower) to guests who viewed or
  responded (upper). Host views after sharing cannot be separated (≈ 6 % false opens).
- **Conversion**: responded by guest ÷ upper open bound, shown as a lower bound («≥»); its upper
  bound is trivially 100 % and is not shown.
- **Visits**: counted views sessionized per guest with the 30-minute rule.
- **Guests without `first_shared_at`**: counted apart (total, viewed, responded) and outside every
  bound.
- **Depth**: not estimated. Legacy `view_percentage` is saturated at 100 % and does not track
  measured depth; since 2026-10-12 the ledger also raises it to the measured milestone.

The admin API returns the estimate with
`GET /api/dashboard/admin/engagement/ranking?level=historical` (`eventType` optional; unknown values
→ 400; 503 until the routine exists). The dashboard shows it in the «Histórico (estimado)» tab with
the method version and its cleaning rules.

### Ranking query v2 (phase 2.1)

`list_invitation_engagement_ranking_v2(p_event_type text default null)` (`20261013150000`,
`security definer`, `service_role` only) starts from every published client invitation
(`kind = 'client'`, not archived) and left-joins its chosen snapshot (final over rolling), so
invitations without activity are listed. Per row it returns identity, event type and date, event
status (`upcoming`, `past`, `unknown`; event-local date in `America/Chihuahua`), activity state
(`measured` or `none`), public access, design (snapshot design, or the latest published content when
there is no snapshot — never repository definitions), confirmation mode, measured and inferred
counts and rates, and `sample_state`. A null event type returns all types; the application ranks
within each event type. Grouping keys offered: theme preset, personalized access variant, RSVP
access mode. Font, music, confirmation mode, event status, activity and public access are filters
whose values come from the rows, so new designs classify themselves.

Ranking rules applied by the application:

- An invitation ranks within its event type when its sample is eligible (≥ 20 shared guests), it is
  enabled, and the metric is measurable for it. The five-invitation threshold applies to
  design-group comparisons only.
- Response rate and conversion ignore invitations that confirm over WhatsApp (`whatsapp` or `both`):
  those replies never reach the database, so both rates are understated.
- Without any measured open the conversion upper bound is trivially 100 % and is not shown.

### Demo engagement (phase 2.1)

Demos have no guests and never produce snapshots. Their design retention comes from anonymous
`tracking_events` (`route_class = 'demo'`, `is_internal = false`) over the last 30 or 60 days (the
Comercial period helper). Sessions are the `demo_viewed` sessions of each `demo_slug`; scroll depth
and contacts carry no slug and are attributed through those sessions. Per demo:

- **Rebote**: share of sessions that never reached the 25 % depth bucket;
- **Llega al 50 / 75 / 100 %**: share of sessions whose deepest bucket reached each level (buckets
  25, 50, 75, 90, 100);
- **Mayor abandono**: the bucket transition after 25 % that loses the largest share of sessions
  (bounce is reported apart because it would hide every later drop);
- **Contactos / 100**: sessions with `cta_clicked` or `whatsapp_contact_clicked` per 100 sessions.

A demo ranks within its event type with at least 100 sessions in the period. Demos that left the
repository but still have sessions are listed as retired. Short pages reach the end more easily, so
demos are compared against demos of similar length. Demo and client figures are never shown in the
same table; the sales funnel stays in the Comercial demo report.

## Privacy notice requirements

The privacy policy (`src/pages/privacidad.astro`) must state, in Spanish ("usted"):

- that guest invitation opens, reading depth, and device class are recorded;
- that per-guest data is shown only to the event host and is not shared with third parties;
- the retention: identifiable for 180 days after the event, then anonymized;
- that anonymous aggregated statistics are kept to improve the service.
